# 例子

## 例 1：配置文件和客户端各改一套

起初树上（或代码里）有两个功能：

- 配置文件：启动时读 `config.toml`，校验写在 `load_toml()` 里
- 客户端设置：设置页保存到数据库 `settings` 表，`save_settings()` 里另写一套校验

问题：客户端改的值重启后被配置文件覆盖；同一个端口号，配置文件允许填 0，客户端不允许。

判定：改的是同一组运行配置，用户看到的结果相同，校验本该一样，所以是同一个节点。

合并后（在「核心功能」下）：

```markdown
### F1 运行配置
- 效果：查看和修改运行配置，修改后不重启即生效
- 数据源：`config.toml`（以它为准，数据库不再存配置）
- 核心实现：`config::ConfigService`（校验、保存、通知生效）
- 界面：配置表单 `ConfigForm`（字段和提示文字跟着 `ConfigService` 的校验规则走）
- 入口：
  - 配置文件：手工编辑 `config.toml`，监听文件变化 → `ConfigService::reload`
  - 客户端：设置页 → `PUT /api/config` → `ConfigService::update`
- 依赖：无
- 状态：已上线
```

「已并入与已删除」表加一行：`F2 客户端设置 | 并入 F1 | 和配置文件改的是同一份配置`。端口号能不能填 0 是冲突项，问用户留哪种。

## 例 2：四个入口合成一个功能

起初有四个功能各自创建账号：后台「新增用户」、注册页、LDAP 同步、管理员 CSV 导入。四处各写一遍用户名校验、密码规则、默认角色。

判定：都写 `users` 表，结果都是多一个能登录的账号，规则本该一样，所以是一个节点「账号创建」，原来的四个功能是它的四个入口。

- 用户名校验、密码规则、默认角色、重名处理进核心实现。
- 各入口独有的部分留在入口里做转换：CSV 导入逐行调用并汇总成功和失败，LDAP 同步按定时任务逐条调用。
- LDAP 同步里的「停用离职账号」是另一个效果，挂到「账号停用」节点的入口下。一个入口可以出现在多个节点下。

```markdown
### F3 账号创建
- 效果：新增一个可登录的账号，带默认角色
- 数据源：`users` 表
- 核心实现：`accounts::create_account()`
- 界面：账号表单 `AccountForm`，后台新增和注册页共用（用户名、密码规则提示）
- 入口：
  - 界面：用户管理页「新增」→ `POST /api/users` → `create_account()`
  - 界面：注册页 `/signup` → `POST /api/signup` → `create_account()`
  - 定时任务：`ldap_sync` 逐条 → `create_account()`
  - 文件导入：用户管理页「导入 CSV」逐行 → `create_account()`
- 依赖：无
- 状态：已上线
```

## 例 3：看着像新功能，其实不是

已有 F1 运行配置（效果：查看和修改运行配置）。

| 需求 | 容易做成 | 应该是 |
|---|---|---|
| 加配置导入导出 | 新功能「配置导入导出」，自己读写配置文件 | F1 的两个新入口。导入就是批量修改，走 `ConfigService::update`；导出就是查看，走 `ConfigService::get` |
| 改错配置要能回到上一版 | 新功能「配置备份」 | F1 的子功能 F1.1「配置历史与回滚」。由核心实现在保存时写历史，回滚也走核心实现 |
| 每个租户单独一套配置 | 新功能「租户配置」，另建一张表 | 改 F1 的效果和数据源：配置按租户区分，所有入口带上租户 |
| 配置改动后通知管理员 | 把发通知写进 F1 的核心实现 | 新扩展功能「配置变更通知」，依赖 F1。去掉它配置照常能改 |

## 例 4：同一份数据，几个页面几个样子

起初：

- 订单列表的状态列显示「处理中」，订单详情显示「进行中」，颜色也不同。
- 概览卡片的「未完成」条数是页面自己用 `status !== 'closed'` 算的，列表筛选「未完成」走接口，两个数对不上。
- 设置页能改通知邮箱，个人中心弹窗也能改，两个表单各写一套邮箱格式校验。

判定：都不是新功能。订单状态和未完成条数属于已有节点「订单」，两处改邮箱是已有节点「通知设置」的两个页面入口。

改法：

- 状态名称和颜色收到一处定义，列表、详情、概览都用它，登记到节点「界面」。
- 「未完成」怎么算是业务规则，放进核心实现，接口返回筛选条件或条数，概览和列表用同一个。
- 两处改邮箱用同一个表单组件，格式校验以接口返回的错误为准。

```markdown
### F4 订单
- 效果：查看订单和订单状态，按状态找订单
- 数据源：`orders` 表
- 核心实现：`orders::OrderService`（状态流转、未完成的判定）
- 界面：状态显示 `web/src/orders/status.ts`（名称、颜色）；订单卡片 `OrderCard`
- 入口：
  - 页面：订单列表 `/orders` → `GET /api/orders?state=open`
  - 页面：订单详情 `/orders/:id` → `GET /api/orders/:id`
  - 页面：概览卡片「未完成」→ `GET /api/orders/count?state=open`
- 依赖：无
- 状态：已上线
```

只在前端的功能同样写成节点。例如「列表记住上次的筛选条件」：数据源写「URL 查询参数（以它为准），浏览器本地存储只存最近一次」，入口是列表页，界面是筛选栏组件。

## 例 5：界面需求先查界面与交互

已有：页面表里「订单列表 `/orders`，运营用，回答『哪些订单要我处理』，布局 L1」；页面布局 L1 列表页、L2 详情页；任务流程 T2 客户申请退款（从订单详情发起）；交互模式 P1 删除、P2 列表筛选；用词表里同一概念叫「订单」。

| 需求 | 容易做成 | 应该是 |
|---|---|---|
| 加一个「待处理订单」页面 | 新开 `/orders/pending`，另写一套列表 | 订单列表已经在回答这个问题。加一个筛选项或分段，筛选条件写进 URL（P2） |
| 退款记录要能删除 | 页面里自己写一个浏览器 `confirm()` | 照 P1：退款不可撤销，用 `ConfirmDialog` 写明删的是哪一笔 |
| 新页面标题写「交易明细」 | 直接写「交易」 | 查用词表，同一概念叫「订单」，标题写「订单明细」 |
| 给客户看的数据看板 | 塞进运营的概览页 | 使用人群和要回答的问题都不同，页面表加一行新页面 |
| 批量关闭订单 | 在订单页自己做勾选和确认 | 交互模式里没有批量操作，先加一条 P4（勾选方式、确认、部分失败怎么提示），再在订单页按 P4 做 |
| 新增一个优惠券列表页 | 自己排版，点一行弹抽屉 | 列表页用 L1：筛选栏在上方，点一行进详情页。觉得抽屉更好，就把它当成改 L1 来提，改了所有列表页一起改，不在一页上单独用 |
| 客服要能替客户发起退款 | 在客服工单里另做一套退款表单和审批 | T2 已经是退款流程。客服工单「代客退款」作为 T2 的第二个起点，填原因、审批、通知沿用同一套 |
| 设计师给了订单详情新设计稿 | 文件放进设计目录就开始改页面 | 设计稿路径写到页面表「订单详情」那一行；新稿和 L2 详情页布局不同的，先判定是改 L2 还是这一页例外，再改页面 |
